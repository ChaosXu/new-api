# 在线支付充值

## 参与者

| 参与者 | 类型 | 职责 |
| --- | --- | --- |
| 普通用户 | 用户角色 | 发起充值订单并完成支付 |
| 支付网关 | 外部系统 | 易支付/Stripe/Creem/Waffo/Waffo-Pancake 处理实际扣款 |
| 网关接入层 | 系统 | 合规前置、订单创建、回调验签、幂等入账、人工补单 |
| 管理员 | 用户角色 | 充值未到账时人工补单 |
| 关系数据库 | 外部系统 | 持久化 topup 订单、user.quota |

    G5 -- 是 --> CB7[标 status=success + IncreaseUserQuota amount*QuotaPerUnit]
    CB7 --> CB8[RecordTopupLog 记录充值日志]
    CB8 --> END_OK([End - Success：额度到账])

    %% 人工补单补偿路径
    WAIT -. 超时未回调 .-> M1([管理员发现未到账])

## 流程描述

在线支付支持易支付、Stripe、Creem、Waffo、Waffo-Pancake 等多渠道，核心链路一致：**创建订单 → 支付 → 回调入账**，并辅以人工补单与过期补偿两条异常闭环。

**创建订单**（如 `controller/topup.go:189` `RequestEpay`）校验最小充值额、实付金额（含分组倍率与折扣）、支付方式可用性、支付渠道已启用（合规+凭证齐全）。通过后生成 `tradeNo`、落库 `pending` 订单、拉起支付页面。

**回调入账**（如 `topup.go:310` `EpayNotify`、`topup_stripe.go:147` `StripeWebhook`）是核心幂等环节：先校验渠道 webhook 启用状态，再**验签**（易支付 `client.Verify`、Stripe `webhook.ConstructEvent`、Waffo-Pancake HMAC）。验签通过后采取"先响应后处理"策略（立即回 `success` 避免网关超时重试），再用 `LockOrder` 订单级互斥锁与数据库行锁双重防并发。入账前校验订单存在性、`PaymentProvider` 匹配（防跨网关回调攻击）、`status==pending`；已处理的订单幂等返回不重复入账。通过后标 `success`、增加额度、记录日志。

**人工补单**（`topup.go:495` `AdminCompleteTopUp` → `model.ManualCompleteTopUp`）是回调缺失时的补偿：管理员触发，走与回调相同的订单级锁与幂等逻辑完成入账。

**过期补偿**（Stripe）在 session 过期时将订单标记为 `expired`，关闭悬挂订单。

横切的安全设计：所有支付渠道启用判定（`payment_webhook_availability.go`）都以 `IsPaymentComplianceConfirmed` 为第一道前置；Waffo-Pancake 还通过路由 `:env` 段 + `event.Mode` 匹配实现 test/prod 环境隔离。
