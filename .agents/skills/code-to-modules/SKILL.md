## 目的

针对 `specs/03-ARCH/L2/components.md` 中已识别的**某一个组件**，从其源码中归纳出全部**模块**，分为**内部模块**（本组件源码包）和**导入模块**（第三方依赖）。产出以**模块为单位**组织：

| 产出物 | 说明 | 如何做 |
| --- | --- | --- |
| `modules.md` | 全部模块的**可点击索引**：按职能分组列模块名/路径/职责/链接；第三方依赖按职能分类汇总 | 见"工作流程"第 1-5、8 步 |
| `<分组>/<模块>.md` | 每个**非同构**模块一个独立文件：职责 + 直接依赖（内部） | 见"工作流程"第 6-7 步 |
| `<分组>-<同构组>.md` | **同构折叠组**（如 39 个同类适配器）汇总到单文件：共性依赖 + 各特例 | 见"工作流程"第 6-7 步 |

每个模块的详情聚合在它自己的文件里（对齐 C4 L3"每个模块一张独立卡片"），`modules.md` 作为导航索引提供全局视图。

## 前置条件（强制）

1. **必须存在 `specs/03-ARCH/L2/components.md`**。若文件缺失，立即停止并提示用户先运行 `code-to-components` skill。
2. **必须由用户指定目标组件名**（即 `components.md` 表中"组件名"列的值）。若用户未指定且 `components.md` 中有多个组件，先询问用户要归纳哪一个；不要默认取第一个。
3. 从 `components.md` 的"路径"列取得目标组件的根目录，后续所有扫描都以此为根，不得越界到其他组件的目录。

## 关键概念

### 模块定义

**模块**：编译/打包进同一组件制品、不独立部署的代码单元。区分两类：

- **内部模块**：位于目标组件源码树内、属于该组件的源码包/目录。
- **导入模块**：来自第三方的外部依赖（如 Go `require`、npm `dependencies`、Maven `<dependencies>`、Python `requirements`），不含指向本仓库内部的 `replace`/workspace 引用（这些归入内部模块）。

与组件的根本区别：**模块没有独立运行入口、不产出独立制品**，只是被组件制品编译/打包进去。

### 划分原则

- **内部模块**：位于本组件源码树内、属于该组件的源码包/目录。
- **导入模块**：来自第三方的外部依赖，不含指向本仓库内部的 `replace`/workspace 引用（这些归入内部模块）。
- 模块没有独立运行入口、不产出独立制品，只是被组件制品编译/打包进去。

### 粒度总则

- **内部模块展开到所有叶子包**：递归列出目标组件源码树内的每一个源码包/源码目录，不合并、不折叠（同构折叠见下条，是产出组织层面的折叠，不影响"识别"层面枚举齐全）。
- **同构折叠（产出组织）**：一批叶子模块若满足**任一**通用原则则折叠到单文件汇总，不各自独立成文件：
  1. **实现同一接口的同类实现**：如 39 个渠道适配器都实现同一 `Adaptor` 接口。
  2. **内容极少且依赖结构雷同的同构目录**：如某 feature 下的 `lib/`/`hooks/` 等零星工具目录。
  - 各语言**特定的同构判定信号**（看什么标志判定）见 `references/<语言>.md` 的"同构折叠判定信号"小节，按识别到的技术栈按需读取。
- **按职能分组组织文件**：模块文件按职能归入分组子目录（英文短目录名，如 `entry`/`infra`/`relay-core`）。中文职能名在 `modules.md` 索引的分组标题里注明。
- **通用排除项**（不计入内部模块）：产物目录（`dist`/`build`/`out`/`target`）、依赖目录（`node_modules`/`vendor`）、测试固件、配置目录、文档目录、CI/构建脚本目录。
- 各语言的**具体粒度规则与语言特定排除项**见 `references/<语言>.md`，按识别到的技术栈按需读取，不要一次全读。

## 输出范围控制（重要）

- **不要把内部推理作为产出**：为了识别模块，通常需要扫描目录、读 import 关系、区分依赖类型。
- **不要在产出中输出**：组件级归纳（由 components.md 承担）、判定推理过程（如"我为什么认为这是模块"）、被排除项的列表、传递依赖的全量展开。
- **必须作为每模块文件产出**：模块的**职责**与**直接依赖（内部）**是事实而非推理过程。直接依赖要列，传递依赖闭包不展开。

## 技术栈参考资料

各技术栈的**数据源**（manifest 证据、import 依赖关系）、**粒度规则**、**同构折叠判定信号**按语言拆分到 `references/`，按需读取对应文件：

| 技术栈 | 识别标志 | 参考文件 |
| --- | --- | --- |
| Go | `go.mod` | `references/go.md` |
| Node/Bun | `package.json` | `references/node.md` |
| Python | `pyproject.toml` / `requirements.txt` / `Pipfile` | `references/python.md` |
| Java | `pom.xml` / `build.gradle` | `references/java.md` |

各语言 reference 的"数据源"表均含三行：内部模块、导入模块、**依赖关系**（采集 import 声明用于每模块文件的正向依赖）。同构折叠的**语言特定判定信号**见各 reference 末尾的"同构折叠判定信号"小节。

多技术栈组件（如同时含 Go 和 Node）按各自规则分别归纳、分别读取对应 reference。

## 工作流程

1. **校验前置**：确认 `specs/03-ARCH/L2/components.md` 存在；取得用户指定的组件名；从表中读取该组件的"路径"作为扫描根。
2. **识别技术栈**：根据扫描根下的 manifest（`go.mod` / `package.json` / `pom.xml` / `pyproject.toml` 等）判断技术栈。
3. **读取语言规则**：按识别到的技术栈，**只读取对应的 `references/<语言>.md`**，获取该语言的内部/导入模块数据源、粒度规则、**依赖关系采集规则**与**同构折叠判定信号**。多技术栈则分别读取各自文件。
4. **枚举内部模块**：按所读语言规则递归扫描源码目录，列出每一个叶子包/源码目录（应用语言特定排除项与通用排除项）。读取每个包的主要源码文件（包注释、`doc.go`、主要导出符号），提炼 1 句中文职责。同时按"依赖关系"采集规则收集每个模块直接 import 的内部模块。
5. **枚举导入模块**：按所读语言规则解析 manifest 的依赖声明，剔除指向本仓库内部的部分；对剩余第三方依赖**按职能分类**（Web 框架、ORM、缓存、鉴权、云 SDK、计费、支付、媒体、序列化、工具集、可观测性、测试、i18n、标准库扩展……），每类以表格列出"依赖 → 用途"。用途据该依赖在本组件源码中的实际 import/调用位置归纳，不要照抄依赖 README。
6. **分组与同构折叠判定**：把内部模块按职能分组（沿用合理的职能边界，为每个分组定一个英文短目录名）。按所读语言的"同构折叠判定信号"，把同构叶子归入折叠组、其余模块标记为独立成文件。
7. **产出每模块文件**：
   - **非同构模块**：读取 `assets/module.md` 模板，每个模块产出一个 `<分组目录>/<模块名>.md`，填入职责与直接依赖（内部）。
   - **同构折叠组**：产出一个汇总文件（如 `adaptors-sync.md`），开头注明共性依赖，表列各叶子的特例（职责差异、非共性依赖）。模块/依赖命名用代码内实际名称，不臆造。删除模板 HTML 注释后交付。
8. **产出 modules.md 索引**：读取 `assets/modules.md` 模板。内部模块按职能分组列表，每行含"文件"列——非同构模块链接到其详情文件，同构折叠组注明见汇总文件。导入模块部分填入第 5 步的分类表。
9. **写入文件**：全部输出到 `specs/03-ARCH/L3/<组件名>/`。其中 `<组件名>` 为 `L2/components.md` 中"组件名"列的值。若目录或分组子目录不存在则创建。

## 与其他 skill 的关系

- **上游**：`code-to-components` 产出 `L2/components.md`，是本 skill 的输入。本 skill 不重新判定组件，只在已确认的组件内做模块归纳。
- **不要越界**：本 skill 只处理**一个**组件。若用户要归纳多个组件，分别调用本 skill，每次产出到各自的 `specs/03-ARCH/L3/<组件名>/`。
