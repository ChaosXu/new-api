## 目的

针对 `specs/03-ARCH/L2/components.md` 中已识别的**某一个组件**，从其代码中**提炼、归类**出全部**逻辑模块**，产出以逻辑模块为单位组织：

| 产出物 | 说明 | 如何做 |
| --- | --- | --- |
| `modules.md` | 全部逻辑模块的**可点击索引**：按功能域分组，列模块名/职责/覆盖代码/链接 | 见"工作流程"第 1-4 步 |
| `<功能域>/<模块>.md` | 每个**逻辑模块**一个独立文件：职责 + 覆盖代码 + 关键契约 + 子能力 + 依赖 | 见"工作流程"第 5-6 步 |

## 前置条件（强制）

1. **必须存在 `specs/03-ARCH/L2/components.md`**。若文件缺失，立即停止并提示用户先运行 `code-to-components` skill。
2. **必须由用户指定目标组件名**（即 `components.md` 表中"组件名"列的值）。若用户未指定且 `components.md` 中有多个组件，先询问用户要归纳哪一个；不要默认取第一个。
3. 从 `components.md` 的"路径"列取得目标组件的根目录，后续所有代码理解都以此为根，不得越界到其他组件的目录。

## 关键概念

### 模块定义（逻辑模块，非目录镜像）

**模块**：代码中一组**协同实现同一职责**的逻辑单元。模块是**从代码职责提炼、归类**出来的，**不与源码目录一一对应**。

判定一个逻辑模块的三条信号：

1. **内聚**：内部代码共同实现一个业务能力或技术能力。
   - 例："计费结算"这个逻辑模块，可能横跨 `service/` 里的计费函数、`relay/common/` 的 `BillingSettler`、`pkg/billingexpr` 的表达式引擎——虽分散在三个目录，但内聚于"计费"这一职责。
2. **边界**：对其他模块通过清晰的接口/契约交互。
   - 例："渠道适配框架"通过 `Adaptor` 接口暴露给"编排入口"。
3. **跨目录允许**：一个逻辑模块可覆盖多个目录；一个目录的代码也可能分属不同逻辑模块。
   - 例："鉴权"模块覆盖 `middleware/`（部分）+ `oauth/` + `service/authz` + `service/passkey`，跨越四个目录。

### 反例（这些不是逻辑模块）

| 误判对象 | 为何不是独立模块 | 正确归类 |
| --- | --- | --- |
| 实现同一接口的多个同类实现（如 39 个渠道适配器） | 它们是同一个逻辑模块的不同实例 | 归为"渠道适配框架"一个模块，实例作为覆盖代码列出 |
| 单个工具目录（如 `common/limiter`） | 内聚于父级能力，不值得单列 | 归入"基础设施·限流"子能力 |
| 一个目录下的所有文件机械各列 | 目录 ≠ 模块 | 按职责归类，多目录可合一模块 |

### 粒度：功能域 + 子能力

模块组织为两层：

- **功能域**（顶层分组）：系统的一个大职责区域（如"中继转发""鉴权""数据访问"）。一个组件通常有 5-8 个功能域。
- **逻辑模块**（功能域下的单元）：功能域内按职责拆出的模块。每个功能域下 **3-5 个逻辑模块**为止，不再细拆。

**粒度判据**：若一个逻辑模块还能清晰拆出 3-5 个独立子能力，且每个子能力都有独立职责，则拆；否则作为一个模块（可在文件内用"子能力"小节描述其内部组成，而不必拆成多个模块文件）。

中等粒度的目标：一个中等组件最终产出 **20-35 个逻辑模块**（非上百个）。

## 输出范围控制（重要）

- **不要把内部推理作为产出**：提炼模块需要通读代码、理解职责、判断内聚性，这些推理过程不产出。
- **不要在产出中输出**：组件级归纳（由 components.md 承担）、判定推理过程、被排除项的列表、传递依赖的全量展开。
- **必须作为每模块文件产出**：模块的**职责**、**覆盖代码**、**关键契约**、**依赖（其他逻辑模块）**是事实而非推理过程。

## 技术栈参考资料

提炼逻辑模块的**通用方法**见本文件。各技术栈的**代码理解切入点**（看什么标志判断职责/契约/内聚）见 `references/<语言>.md`，按识别到的技术栈按需读取：

| 技术栈 | 识别标志 | 参考文件 |
| --- | --- | --- |
| Go | `go.mod` | `references/go.md` |
| Node/Bun | `package.json` | `references/node.md` |
| Python | `pyproject.toml` / `requirements.txt` / `Pipfile` | `references/python.md` |
| Java | `pom.xml` / `build.gradle` | `references/java.md` |

多技术栈组件（如同时含 Go 和 Node）分别理解、分别读取对应 reference。

## 工作流程

1. **校验前置**：确认 `specs/03-ARCH/L2/components.md` 存在；取得用户指定的组件名；从表中读取该组件的"路径"作为根。
2. **通读代码理解职责**：通读组件源码（包注释、主要导出符号、关键调用链），理解每个目录/文件**做什么**。这是提炼的基础——不要跳到"列目录"。
3. **按内聚性归并功能域**：把理解的职责按内聚性归并为 5-8 个**功能域**。归并时以"共同实现的业务/技术能力"为依据，不被目录边界束缚（跨目录归并是常态）。
4. **每域拆逻辑模块**：每个功能域下按职责拆 3-5 个**逻辑模块**。应用反例规则：同类实现不各列、单工具目录不单列。
5. **标注覆盖代码与契约**：为每个逻辑模块列出：它**覆盖**哪些目录/文件（可追溯到代码）、对外暴露的**关键契约**（核心 interface/struct/导出函数）。
6. **列模块间依赖**：确定每个逻辑模块依赖哪些**其他逻辑模块**（以职责为单位，非目录）。依赖据实际调用/引用关系提炼。
7. **产出每模块文件**：读取 `assets/module.md` 模板，每个逻辑模块产出一个 `<功能域>/<模块名>.md`，填入职责、覆盖代码、关键契约、子能力、依赖。
8. **产出 modules.md 索引**：读取 `assets/modules.md` 模板，按功能域分组列全部逻辑模块（模块名 + 职责 + 覆盖代码 + 链接到详情文件）。
9. **写入文件**：全部输出到 `specs/03-ARCH/L3/<组件名>/`。若目录或功能域子目录不存在则创建。

## 与其他 skill 的关系

- **上游**：`code-to-components` 产出 `L2/components.md`，是本 skill 的输入。本 skill 不重新判定组件，只在已确认的组件内提炼模块。
- **下游**：`code-to-*`（L4 写代码说明书）以本 skill 的逻辑模块为单元，每类代码范式写一份 L4。
- **不要越界**：本 skill 只处理**一个**组件。若用户要归纳多个组件，分别调用本 skill，每次产出到各自的 `specs/03-ARCH/L3/<组件名>/`。
