## 目的

针对 `specs/03-ARCH/L2/components.md` 中已识别的**某一个组件**，从其代码中**提炼、归类**出全部**逻辑模块**与**业务流程**，产出两个互补维度：

| 产出物 | 维度 | 说明 | 如何做 |
| --- | --- | --- | --- |
| `modules/<功能域>/<模块>.md` | **静态**（是什么） | 每个**逻辑模块**一个文件：职责 + 覆盖代码 + 关键契约 + 子能力 + 依赖 | 见"工作流程"第 1-6 步 |
| `flows/<流程>.md` | **动态**（怎么流转） | 每个 L3 级别**业务流程**一个文件：时序图 + 流程说明 + 涉及模块 | 见"工作流程"第 7-9 步 |
| `modules.md` | **索引** | 全部模块 + 全部流程的可点击导航 | 见"工作流程"第 6、10 步 |

静态模块卡描述"每个模块是什么"；动态流程描述"一个请求/场景怎么在模块间流转"。两者互补，缺一不可。

## 前置条件（强制）

1. **必须存在 `specs/03-ARCH/L2/components.md`**。若文件缺失，立即停止并提示用户先运行 `code-to-components` skill。
2. **必须由用户指定目标组件名**（即 `components.md` 表中"组件名"列的值）。若用户未指定且 `components.md` 中有多个组件，先询问用户要归纳哪一个；不要默认取第一个。
3. 从 `components.md` 的"路径"列取得目标组件的根目录，后续所有代码理解都以此为根，不得越界到其他组件的目录。

## 目录结构

```
L3/<组件名>/
├── modules.md          # 索引（含"关键流程"入口节 + 模块表）
├── modules/            # 静态逻辑模块（按功能域分组）
│   └── <功能域>/<模块>.md
└── flows/              # 动态业务流程（与 modules/ 平级）
    └── <流程>.md
```

`modules/`（静态结构）与 `flows/`（动态流程）平级，体现两个维度的分界。

## 关键概念

### 逻辑模块（静态，非目录镜像）

**模块**：代码中一组**协同实现同一职责**的逻辑单元。从代码职责**提炼、归类**，**不与源码目录 1:1 对应**。

判定信号：
1. **内聚**：内部代码共同实现一个业务/技术能力（可跨目录）。
2. **边界**：通过清晰的**开放能力**（契约）与其他模块交互。契约是模块对外提供的能力（能力短语，如"统一的上游协议适配能力"），**不是具体的 interface/struct/函数符号**——能力比代码符号更高层、更稳定。
3. **跨目录允许**：一个模块可覆盖多个目录（如"鉴权"跨 middleware/oauth/service/authz/passkey）。

**反例（合并的停止条件）**：实现同一接口的多个同类实现（如 39 个适配器）归为一个模块的**条件是**——实现间共享相同的开放能力集合与相同的依赖图。若某实现暴露了独有能力（流式、异步、退款）或依赖显著不同的外部系统，必须拆为独立模块或显式子能力，不得合并。**删除"单工具目录不单列"的绝对规则**；运维类入口（migrator/seeder/backfill）即使单文件也归入「运维入口」域列出，因为它们是 runbook 单元。

**粒度**：功能域 + 子能力。5-8 个功能域，每域 3-5 个逻辑模块为止。中等组件约 20-35 个逻辑模块。「跨切面/基础设施」域不受 5-8 上限约束（见工作流程第 4 步）。

### 业务流程（动态，L3 级别）

**流程**：一个请求/场景在逻辑模块间**按时间顺序流转**的动态协作。静态模块卡描述"模块是什么"，流程描述"它们怎么协作"。

**L3 级别流程判定标准**（满足以下**任二**即写，避免低价值流程泛滥，也避免漏掉无内部状态的集成流）：
1. **跨多模块协作**：流程经过 ≥3 个逻辑模块。
2. **跨系统协作**：流程跨 ≥1 个外部系统（上游 AI、支付网关、第三方 OAuth）且经过 ≥2 个逻辑模块——覆盖无内部状态但跨系统的集成流（webhook 扇出、同步代理）。
3. **有状态流转或时序意义**：有明显的阶段/状态变化（内部状态如预扣→结算、提交→轮询→完成；或外部状态如上游异步任务状态轮询），不是一次直通的简单调用。

> 删除"难以从单模块理解"这类主观项；判定必须基于上述客观条件。

**反例（不写）**：单模块内 CRUD、无跨模块协作、无跨系统协作——**三者全满足**才排除（如令牌/用户/日志管理：controller→service→model 三层直通，读 controller 即可）。

## 输出范围控制（重要）

- **不要把内部推理作为产出**：提炼模块/流程需通读代码、理解职责与调用链，推理过程不产出。
- **不要在产出中输出**：组件级归纳（由 components.md 承担）、判定推理过程、传递依赖全量展开。**但「源码覆盖矩阵」（含 `dont-list` 项及一句排除理由）是第 3/12 步的强制产出，不受本条限制**——它是完整性审计的唯一痕迹。
- **必须产出**：模块的职责/覆盖代码/契约/依赖；流程的时序图/说明/涉及模块——这些都是**事实**。
- **不臆造调用链**：流程文档的时序图与说明必须据真实代码的函数名/文件行号梳理，不得臆造。

## 技术栈参考资料

提炼逻辑模块的**通用方法**见本文件。各技术栈的**代码理解切入点**（看什么标志判断职责/契约/内聚）见 `references/<语言>.md`，按识别到的技术栈按需读取：

| 技术栈 | 识别标志 | 参考文件 |
| --- | --- | --- |
| Go | `go.mod` | `references/go.md` |
| Node/Bun | `package.json` | `references/node.md` |

## 工作流程

### 第零部分：模板绑定（强制，输出前必做）

0. **模板绑定**：输出任何文件前，逐字复制 `assets/module.md`、`assets/flow.md`、`assets/modules.md` 的章节标题与表头。**禁止**增删表格列、改列名、新增"第三方依赖"节、改章节顺序。本步是防止 schema 漂移（退化回目录镜像）的前置闸门，必须在每次产出时执行。

### 第一部分：提炼逻辑模块（静态）

1. **校验前置**：确认 `L2/components.md` 存在；取得用户指定的组件名；读取其"路径"作为根。
2. **通读代码理解职责**：通读组件源码（包注释、主要导出符号、关键调用链），理解每个目录/文件做什么。
3. **强制枚举源码目录（覆盖完整性闸门）**：用 `find <根> -type d`（排除 `vendor/`、`node_modules/`、`dist/`、`build/`、`out/`、`.venv`）列出**每一个**源码目录。对每个目录做三选一判定：`covered-by-existing-module`（归入某模块）/ `new-module`（需新建模块）/ `type-only-dont-list`（仅类型/配置/产物，不单列）。判定结果记入 `modules.md` 的「源码覆盖矩阵」附录（强制产出，见 `assets/modules.md` 模板）。**矩阵必须 100% 覆盖枚举结果**；未覆盖的目录不得进入下一步。本步是防止整目录被静默跳过的关键，"通读理解"不能替代枚举。
4. **按内聚性归并功能域**：把职责按内聚性归为 5-8 个功能域（以共同实现的能力为依据，不受目录边界束缚）。功能域应**至少包含一个「跨切面/基础设施」域**（缓存、限流、可观测、配置、校验、幂等、重试、错误处理）；该域**不受 5-8 上限约束**，每个有独立开放能力与独立依赖图的基础设施组件各为一个逻辑模块，禁止全部塞进单个"基础设施"模块。
5. **每域拆逻辑模块**：每域按职责拆 3-5 个逻辑模块。应用反例规则（同类实现合并的条件见"关键概念"）。
6. **标注职责、开放能力与覆盖代码**：每模块提炼三项——**职责**（1-2 句核心能力）、**开放能力**（对外提供的若干能力，用能力短语表达，**不是 interface/struct/函数符号**）、**覆盖代码**（覆盖的目录/文件，**禁止用单个裸文件路径形式如 `./x.js` 作为整模块覆盖代码**，防目录镜像回潮）。再加依赖的其他逻辑模块。
7. **产出模块文件 + 索引**：读 `assets/module.md` 模板，每模块产 `modules/<功能域>/<模块>.md`；读 `assets/modules.md` 模板的"内部模块"区填模块表。

### 第二部分：提炼业务流程（动态）

8. **入口族系统核对**（保证不遗漏的关键）：逐项扫描以下 **7 类入口族**，每族要么列出发现的入口、要么显式记 "none"，不得跳过：
   1. **HTTP/REST handler 注册**：路由文件、注解路由、反射注册的全部端点。
   2. **gRPC / GraphQL / WebSocket / SSE handler**：非 REST 的协议入口。
   3. **启动入口**：所有 `main`/`__main__`/CLI 子命令（扫描多个 `cmd/`、`bin/`、`scripts/`，不只根 `main.go`）。
   4. **后台 goroutine / worker / 消费者**：MQ 订阅、事件总线、channel 消费、`go xxx()`。
   5. **定时任务**：cron 表达式注册、`time.Ticker`、scheduler 库（可能在 service 的 `Start()` 里，不全在 main）。
   6. **Webhook / 回调端点**：含动态注册、不在主路由文件的。
   7. **信号 / 文件监听 / 触发器**：`signal.Notify`、fsnotify 等。
   - 各技术栈的具体扫描命令与标志见 `references/<语言>.md`。对每个发现的入口过 L3 过滤（见"关键概念"），排除单模块内纯 CRUD。
9. **梳理每个流程的真实调用链**：对清单中每个流程，通读代码确认其跨模块调用链（函数名/文件行号），明确阶段、状态流转、关键细节（幂等点、事务边界、计费点等）。
10. **产出流程文件**：读 `assets/flow.md` 模板，每个流程产 `flows/<流程>.md`——时序图（参与方用逻辑模块名，不用目录名）+ 逐步说明 + 涉及模块清单（链接 modules/ 模块卡，形成双向呼应）+ 若涉及 AGENTS.md 硬约束则摘录。
11. **索引补"关键流程"入口**：读 `assets/modules.md` 模板的"关键流程"区，分"请求驱动流程"（HTTP/协议入口）与"后台自动流程"（启动/定时/事件入口）两类列流程。

### 第三部分：覆盖校验（强制，收尾闸门）

12. **覆盖校验**：重跑第 3 步的目录枚举。对每个目录，确认它出现在某个模块的「覆盖代码」或「源码覆盖矩阵」的 `dont-list` 行。若有目录两者皆无，回到第 5 步补模块或补矩阵。
13. **结构校验**：(1) `modules/` 下文件数 = `modules.md`「内部模块」表行数；(2) 每个 flow 的「涉及的 L3 逻辑模块」链接目标都存在；(3) 任一模块「覆盖代码」不得是单个裸文件路径形式（防目录镜像回潮）。校验不通过则回退修正。

### 写入路径

全部输出到 `specs/03-ARCH/L3/<组件名>/`（`modules/`、`flows/`、`modules.md`）。目录不存在则创建。

## 与其他 skill 的关系

- **上游**：`code-to-components` 产出 `L2/components.md`，是本 skill 的输入。
- **下游**：`code-to-*`（L4 写代码说明书）以本 skill 的逻辑模块与流程为参考单元。
- **不要越界**：本 skill 只处理一个组件。多个组件分别调用，各产出到各自的 `L3/<组件名>/`。
