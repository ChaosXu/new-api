# 产出物：模块间依赖关系（{组件名}/dependencies.md）

## 是什么

从**某一个组件内部**的模块（已在 `modules.md` 列出）出发，归纳它们**彼此之间**的依赖关系。回答两个 AI 开发最高频的问题：

- **正向**：改动模块 X，会牵动哪些下游模块？
- **反向**：模块 Y 是被广泛依赖的枢纽，改动它要评估哪些消费者？

> **不在本产出物范围**：
> - 模块对**第三方依赖**的关系：已在 `modules.md` 的"导入模块"区覆盖，这里不重复。
> - **传递依赖全量展开**：只列直接依赖，不递归展开传递闭包。
> - 模块清单本身、职责描述：见 `modules.md`。本文件只写"关系"。

## 三部分

| 部分 | 方向 | 粒度 | 回答什么 |
| --- | --- | --- | --- |
| ① 内部模块直接依赖 | 正向（本模块→它依赖的） | 每个有内部依赖的模块一行 | 改这个模块要顺着牵动谁 |
| ② 枢纽模块及其主要消费者 | 反向（枢纽→依赖它的） | 只列枢纽模块 | 动这个枢纽要评估谁 |

## 数据源

跨语言通用：**各源码文件的 import 声明**。语言特定采集规则见 `references/<语言>.md` 的"依赖关系"行，核心是：**剔除标准库与第三方，只留本组件内部的引用**。

| 类别 | 证据来源 |
| --- | --- |
| 内部模块直接依赖 | 各包/各文件的 import 声明，剔除标准库与第三方（manifest 中声明的外部依赖），只留指向本组件源码树内其他模块的引用。Go 的 `replace`/Node 的 `workspaces` 指向仓库内子 module 视为内部依赖。 |
| 枢纽模块 | 由"内部模块直接依赖"反向聚合得出：统计每个模块**被多少模块直接依赖**。 |

### 枢纽模块判定

满足以下**任一**即列为枢纽：

1. **广泛依赖**：被 ≥ 5 个内部模块直接依赖。
2. **核心契约**：定义了被跨模块复用的关键 interface/struct（即使反向依赖数未达阈值，如 `relay/channel` 定义 `Adaptor` 接口、`relay/common` 定义 `RelayInfo`）。

阈值 5 为默认，可视组件规模调整（小组件可降到 3）。

## 怎么做

1. **采集 import**：按所读语言规则，扫描目标组件源码树内所有源码文件，收集每个文件 import 的路径。
2. **剔除外部**：从采集结果中剔除标准库、第三方依赖（manifest 中声明的外部坐标），只留指向本组件源码树内其他模块的引用。
3. **归约到模块**：把文件级 import 归约到**模块级**（如 Go 的 `.../relay/channel/aws` import `.../relay/common` → 模块 `relay/channel/aws` 依赖模块 `relay/common`）。
4. **构建正向边**：得到"模块 → 直接依赖的内部模块"映射。
5. **识别枢纽**：对正向边做反向聚合，按"枢纽模块判定"选出枢纽模块；列出每个枢纽的**主要消费者**（消费者多时可只列代表性/按分组列，不必全量，但需注明"等 N 个"）。
6. **填模板**：读取 `assets/dependencies.md`，把正向边填入第 1 节、枢纽反向填入第 2 节。模块命名用代码内实际名称，不臆造。
7. **删模板注释**：删除模板中的 HTML 注释后交付。

## 模板

- `assets/dependencies.md`
