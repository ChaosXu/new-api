## 目的

1. 基于现有代码，识别端到端完整业务链路，输出标准化 BPMN 业务模型（以 Mermaid flowchart 表示）。
2. 清晰表达参与者、业务活动、流转顺序、分支规则与异常场景，并保证主路径与异常路径均闭环。

## 关键概念

### BPMN 2.0 元素速查

- **池 / 泳道（Pool / Lane）：** 表示业务参与方（业务角色）或系统 / 外部服务，每个泳道内的活动由该角色负责。
- **任务（Task）：** 单一业务动作的最小执行单元，必须可在一个角色内完成。
- **子流程（Subprocess）：** 多个任务的聚合，可被复用或单独展开。
- **事件（Event）：** Start Event 触发流程、End Event 结束流程；Intermediate Event 表达等待或触发；Error / Timer / Message 事件用于异常与异步交互。
- **网关（Gateway）：**
  - 排他网关（Exclusive, XOR）：从多条路径中选择一条
  - 并行网关（Parallel, AND）：所有出向路径同时执行
  - 包容网关（Inclusive, OR）：条件满足的路径都会执行
  - 事件网关（Event-based）：等待外部事件后再选择路径
- **顺序流（Sequence Flow）：** 同一泳道或跨泳道活动之间的控制流转。
- **消息流（Message Flow）：** 不同 Pool 之间的信息交互（不同于控制流转）。
- **边界事件（Boundary Event）：** 附着在任务上，捕获超时、错误、消息等以触发补偿或替代路径。
- **补偿（Compensation）：** 已完成任务的回滚动作，常与业务取消 / 失败事件配对使用。

### 端到端业务流程的判定准则

- 至少包含一个明确的 **Start Event** 和至少一个 **End Event**。
- 所有业务角色与系统 / 外部服务都已作为泳道出现，且每个泳道至少承担一个活动。
- 主路径与每条异常路径都形成闭环（不存在"流程走丢"的悬挂节点）。
- 网关判定条件必须可机读（布尔表达式、规则 ID 或数据条件），不允许"满足条件即通过"等模糊表述。

### 反模式（这不是什么）

- **不是系统时序图：** 重点在业务活动，不在接口或消息字段。
- **不是用例图：** 流程中的活动是"动作"，而不是角色能力清单。
- **不是任务清单：** 流程强调流转、分支与异常，不是单纯 TODO。
- **不是 UI 交互稿：** 活动描述聚焦业务意图，不绑定具体页面控件。

## 应用

### 第 1 步：理解角色使用的功能

- **理解用户角色**： 请用用户提供要发分析的用户角色清档（如`01-PRD/01-用户角色清单.d`）。
- **分析角色相关的功能**： 对于每个角色，阅读项目中的代码，识别出该角色使用的功能。

---

### 第 2 步：理解功能实现的业务流程

- **分析每个功能的业务逻辑**： 对于每个功能，阅读相关实现代码，分析它实现的业务逻辑。
- **提炼业务流程**： 是否存在多个功能实现的业务逻辑是一个更大的业务流程的一部分？将此种情况的业务逻辑归纳按照BPNM2.0规范，归纳成一个业务流程。

---

## 第 3 步：输出业务流程

- **业务流程分组** 但将相关的业务流程按照所属业务分组在一起，每个分组创建一个`specs/01-PRD/03-业务流程/{业务分组}/`目录。
- **业务流程输出** 使用 `assets/template.md` 获取完整的填写结构，按照模版的格式填写。一个业务流程一个md文件，输出到`specs/01-PRD/03-业务流程/{业务分组}/`目录下。
- **质量检查**：不遗漏业务流程，不增加代码中不存在的业务流程，业务流程不存在重复或交叉。
