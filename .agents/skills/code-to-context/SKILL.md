## 目的

从当前项目的代码中归纳出**系统上下文**——即 C4 模型的 Level 1（System Context）：把整个系统视为一个黑盒，只描述**系统与外部世界的边界和交互**，不涉及系统内部的任何结构。

产出一份文档 `specs/03-ARCH/L1/context.md`，严格按内置模板填写，包含：

- **系统职责**：一句话说明系统对外提供什么能力。
- **系统上下文图**：一张 Mermaid 图，系统居中，连接外部角色与外部系统。
- **外部角色清单**：与系统交互的人类角色，按权限层级粗粒度归纳。
- **外部系统清单**：系统依赖或交互的外部软件服务/基础设施，按职能分类。

## 关键概念

### 系统上下文定义

**系统上下文**：把系统作为一个整体（黑盒），描述其与外部世界的边界。只回答两个问题：

1. 谁在使用这个系统？（**外部角色**，即人）
2. 这个系统与哪些外部系统交互？（**外部系统**，即软件服务/基础设施）

**核心约束：不涉及系统内部结构。** 系统内部由哪些容器/组件/模块组成，是 `code-to-components` 和 `code-to-modules` 的职责。本 skill 只画"系统 ↔ 外部"的边界。

### 外部角色（人）

**外部角色**：与系统交互的人类用户，按**权限层级**粗粒度归纳为抽象角色，不细分到具体业务角色。

典型抽象层级（按实际代码中体现的权限分层取值）：

| 抽象角色 | 识别标志 |
| --- | --- |
| 未认证访客 | 可访问公开路由/端点，无需登录 |
| 认证用户 | 需登录/持凭证访问受保护资源 |
| 管理员/特权用户 | 拥有后台管理、系统配置等高权限 |

判定时以代码中实际存在的认证/授权分层为准；若系统只有一层认证，则只列"认证用户"。

### 外部系统

**外部系统**：本系统在运行时主动调用其能力、与之有业务交互的外部软件服务，系统本身不可控。例如：上游 AI 提供商、第三方 API、支付网关、OAuth 身份提供商、邮件/SMS 网关、人机验证服务等。

判定要点：外部系统是系统**对外打交道、完成业务功能**所依赖的对话方（供应商/合作方），而非承载系统自身运行的实现设施。

**反模式（这些不是外部系统）**：

| 误判对象 | 为何不是 |
| --- | --- |
| 支撑系统运行的内部设施（数据库、缓存、消息队列、对象存储等） | 属于"系统如何实现存储/协调"的内部实现决策，不参与系统对外的业务对话；归 L2/L3 的部署/运行时视图，不计入 L1 系统上下文 |
| 系统内部的可独立部署容器（如同一仓库的另一个服务） | 属于系统内部，由 `code-to-components` 归纳 |
| 第三方库/框架（编译/打包进系统制品，以 import/require 方式消费） | 属于系统内部依赖，由 `code-to-modules` 的"导入模块"归纳，不在此列 |
| 开发态/构建态工具链（编译器、打包器、linter） | 不参与运行时交互，不计入系统上下文 |

关键区分点：**外部系统是系统为完成对外业务而调用的外部能力方**（如转发 AI 请求、发起支付、OAuth 登录）；**数据库/缓存等是承载系统自身运行的设施**，是"系统怎么落地"的内部决策，属 L2/L3，不进 L1。

## 数据源（判定证据）

按"要识别什么 → 去哪里找证据"组织，跨技术栈通用：

| 要识别 | 证据来源（跨语言通用） |
| --- | --- |
| 外部角色 | 认证/授权机制（JWT、Session、Passkey/WebAuthn、OAuth、API Key、Basic Auth）；路由分组（公开路由 vs 认证路由 vs 管理员守卫路由）；前端路由的访问控制分组（如未认证区/认证区/管理区）；RBAC/权限策略定义 |
| 上游服务 | 出站 HTTP/WebSocket/RPC/gRPC 客户端调用；渠道/适配器/provider 目录（封装了对外部服务调用的代码模块）；渠道类型/提供商类型枚举常量；webhook 回调配置 |
| 外部服务凭证 | 环境变量与配置项中指向上游服务的地址、端口、密钥、Token（如 `*_API_KEY`、`*_ENDPOINT`） |
| 系统职责 | README、主入口文件、路由表顶层端点分组、Dockerfile/部署描述、package/模块描述文件中的 `description` |

## 工作流程

1. **界定系统边界**：从仓库根的 manifest（`go.mod` / `package.json` / `pom.xml` / `pyproject.toml` 等）和部署描述（Dockerfile、CI 配置）确认系统对应的主制品与对外接口形态（HTTP 服务 / CLI / 桌面应用 / 静态站点）。系统 = 本仓库产出并运行的全部内容，不纠结内部分几个容器。
2. **识别外部角色**：扫描认证/授权中间件、路由分组的访问控制、前端路由守卫，按权限层级归纳为粗粒度抽象角色（未认证访客 / 终端用户 / 管理员等，以代码实际分层为准）。
3. **识别外部系统（仅上游服务）**：扫描出站调用、渠道/适配器目录、提供商枚举，归纳本系统为完成对外业务而主动调用的外部服务。
   - 剔除支撑设施：数据库、缓存、消息队列、对象存储等承载系统运行的设施**不列入**——它们是"系统怎么落地"的内部决策，归 L2/L3 部署/运行时视图。
   - 剔除：编译进制品的第三方库（归 `code-to-modules`）、系统内部的其他容器、构建态工具链。
4. **归纳系统职责**：从 README、主入口、路由表提炼系统对外提供的一两项核心能力，浓缩为一句话。
5. **绘制上下文图**：用 Mermaid `graph` 或 `flowchart`，系统节点居中，左侧连外部角色（人或角色用圆角节点 `()`），右侧连外部系统（存储/服务用圆柱 `[()]` 或方框），边上标注交互方式（如"HTTP API""转发""读写""支付回调"）。
6. **按模板产出**：读取模板 `assets/context.md`，填入系统职责、Mermaid 图、外部角色表、外部系统表。删除模板中的 HTML 注释后交付。
7. **写入文件**：输出到 `specs/03-ARCH/L1/context.md`。若目录不存在则创建。

## 输出范围控制（重要）

- **不要把内部推理作为产出**：为了界定系统边界和识别外部实体，通常需要扫描路由、读 manifest、区分依赖类型。
- **不要在产出中输出**：系统内部的容器/组件/模块清单、判定推理过程、被排除项的列表、第三方库的全量依赖列表。读者只看到"系统 ↔ 外部"的边界。
